# Spring 断点实验手册

> 每个实验设计了「目标 → 准备 → 断点 → 操作步骤 → 预期观察 → 结论」的完整流程。
> 建议在 `实验代码/` 目录下创建对应的测试类，配合本手册逐步调试。

## 实验一：观察三级缓存解决循环依赖

### 🎯 目标
亲眼看到三级缓存的工作过程：ObjectFactory 如何被调用、早期引用如何升级到二级缓存。

### 📦 准备代码

```java
@Component
public class ServiceA {
    @Autowired
    private ServiceB serviceB;
    
    public void hello() { System.out.println("A.hello"); }
}

@Component
public class ServiceB {
    @Autowired
    private ServiceA serviceA;
    
    public void hello() { System.out.println("B.hello"); }
}

// 启动类
public class CircularDependencyTest {
    public static void main(String[] args) {
        AnnotationConfigApplicationContext ctx =
            new AnnotationConfigApplicationContext("com.example");
        ctx.getBean(ServiceA.class).hello();
    }
}
```

### 🔴 断点位置

| 编号 | 文件 | 方法 | 行号关键词 | 作用 |
|------|------|------|-----------|------|
| BP1 | DefaultSingletonBeanRegistry | `addSingletonFactory()` | `this.singletonFactories.put` | 观察三级缓存放入 |
| BP2 | DefaultSingletonBeanRegistry | `getSingleton(beanName, true)` | `singletonFactory.getObject()` | 观察三级缓存被调用 |
| BP3 | DefaultSingletonBeanRegistry | `addSingleton()` | `this.singletonObjects.put` | 观察一级缓存放入 |
| BP4 | AbstractAutoProxyCreator | `getEarlyBeanReference()` | `wrapIfNecessary` | 观察早期 AOP 代理创建 |

### 📝 操作步骤

1. 在 BP1 打断点，启动程序
2. **第一次命中 BP1**：观察 Variables 面板
   - `beanName` = `"serviceA"`
   - `singletonFactory` 是一个 lambda（ObjectFactory）
   - 检查 `singletonFactories` Map：现在只有 serviceA
3. 按 F9 继续，程序会在 `populateBean()` 中发现需要注入 serviceB
4. **第二次命中 BP1**：`beanName` = `"serviceB"`
5. 继续，serviceB 的 `populateBean()` 发现需要注入 serviceA
6. **命中 BP2**：这是关键！
   - 观察 `beanName` = `"serviceA"`
   - 一级缓存：miss（serviceA 还没创建完）
   - `isSingletonCurrentlyInCreation("serviceA")` = **true**
   - 三级缓存：**hit**！调用 `singletonFactory.getObject()`
   - 返回值放入二级缓存 `earlySingletonObjects`
7. serviceB 完成创建，**命中 BP3**：serviceB 放入一级缓存
8. 回到 serviceA 的属性注入，继续完成
9. **再次命中 BP3**：serviceA 放入一级缓存

### ✅ 预期观察

| 时间点 | 一级缓存 | 二级缓存 | 三级缓存 | singletonsCurrentlyInCreation |
|--------|---------|---------|---------|------------------------------|
| A 实例化后 | — | — | A 的 ObjectFactory | {A} |
| B 实例化后 | — | — | A, B 的 ObjectFactory | {A, B} |
| B 注入 A 时 | — | A 的早期引用 | B 的 ObjectFactory | {A, B} |
| B 完成创建 | B | A 的早期引用 | — | {A} |
| A 完成创建 | A, B | — | — | {} |

### 💡 结论
- 三级缓存的 ObjectFactory **只在发生循环依赖时才被调用**
- 如果没有循环依赖，ObjectFactory 永远不会被调用，Bean 直接放入一级缓存
- 二级缓存保证同一个早期引用不会被 ObjectFactory 重复创建

## 实验二：观察 AOP 代理创建时机

### 🎯 目标
验证 AOP 代理是在 `postProcessAfterInitialization` 中创建的，而非实例化时。

### 📦 准备代码

```java
@Component
public class OrderService {
    @Transactional
    public void createOrder() {
        System.out.println("创建订单");
    }
}

@Aspect
@Component
public class LogAspect {
    @Before("execution(* com.example.OrderService.*(..))")
    public void log() {
        System.out.println("日志切面");
    }
}
```

### 🔴 断点位置

| 编号 | 文件 | 方法 | 作用 |
|------|------|------|------|
| BP1 | AbstractAutowireCapableBeanFactory | `createBeanInstance()` 返回处 | 观察实例化后的原始对象 |
| BP2 | AbstractAutoProxyCreator | `postProcessAfterInitialization()` | 观察代理判断入口 |
| BP3 | AbstractAutoProxyCreator | `wrapIfNecessary()` 的 `createProxy()` 行 | 观察代理创建 |

### 📝 操作步骤

1. 在 BP1 打断点，条件设为 `beanName.equals("orderService")`
2. 命中后观察：此时 bean 是 **OrderService 原始对象**（不是代理）
3. 继续到 BP2，观察：
   - `bean.getClass().getName()` 仍然是 `com.example.OrderService`
4. 继续到 BP3，观察：
   - `specificInterceptors` 不为 null（找到了匹配的 Advisor）
   - `createProxy()` 被调用
5. 步过 `createProxy()` 后观察返回值：
   - `proxy.getClass().getName()` 包含 `$$SpringCGLIB$$`

### ✅ 预期观察
- 实例化时（BP1）：普通对象
- `postProcessAfterInitialization`（BP2-BP3）：创建 CGLIB 代理
- 最终放入容器的是代理对象，不是原始对象

## 实验三：观察 @Transactional 的提交与回滚

### 🎯 目标
验证 RuntimeException 回滚、受检异常不回滚的默认行为。

### 📦 准备代码

```java
@Service
public class PaymentService {
    @Transactional
    public void payWithRuntime() {
        // 模拟数据库操作
        throw new RuntimeException("支付失败");
    }
    
    @Transactional
    public void payWithChecked() throws Exception {
        // 模拟数据库操作
        throw new Exception("支付失败"); // 受检异常
    }
    
    @Transactional(rollbackFor = Exception.class)
    public void payWithCheckedFixed() throws Exception {
        throw new Exception("支付失败"); // 配置了 rollbackFor
    }
}
```

### 🔴 断点位置

| 编号 | 文件 | 方法 | 作用 |
|------|------|------|------|
| BP1 | TransactionAspectSupport | `invokeWithinTransaction()` 的 `createTransactionIfNecessary` 行 | 观察事务创建 |
| BP2 | TransactionAspectSupport | `completeTransactionAfterThrowing()` | 观察异常处理决策 |
| BP3 | AbstractPlatformTransactionManager | `processRollback()` | 确认回滚执行 |
| BP4 | AbstractPlatformTransactionManager | `processCommit()` | 确认提交执行 |

### 📝 操作步骤

**测试 1：RuntimeException**
1. 调用 `payWithRuntime()`
2. BP1 命中：观察 `txAttr`（传播行为、隔离级别）
3. BP2 命中：观察 `txAttr.rollbackOn(ex)` → **true**
4. BP3 命中：确认走了回滚逻辑 ✅

**测试 2：受检异常**
1. 调用 `payWithChecked()`
2. BP2 命中：观察 `txAttr.rollbackOn(ex)` → **false** ⚠️
3. BP4 命中：确认走了 **提交** 逻辑！数据不会回滚！

**测试 3：配置 rollbackFor**
1. 调用 `payWithCheckedFixed()`
2. BP2 命中：`txAttr.rollbackOn(ex)` → **true** ✅
3. BP3 命中：确认走了回滚逻辑

### 💡 结论
- 默认：RuntimeException/Error 回滚，受检异常 **提交**（不回滚！）
- 最佳实践：始终配置 `@Transactional(rollbackFor = Exception.class)`

## 实验四：观察 DispatcherServlet 请求分发

### 🎯 目标
追踪一个 HTTP 请求从进入 DispatcherServlet 到返回 JSON 的完整链路。

### 📦 准备代码

```java
@RestController
@RequestMapping("/api")
public class UserController {
    @GetMapping("/user/{id}")
    public User getUser(@PathVariable Long id) {
        return new User(id, "张三");
    }
}

@Component
public class AuthInterceptor implements HandlerInterceptor {
    @Override
    public boolean preHandle(HttpServletRequest request,
                             HttpServletResponse response, Object handler) {
        System.out.println("认证拦截器 preHandle");
        return true;
    }
}
```

### 🔴 断点位置

| 编号 | 文件 | 方法 | 作用 |
|------|------|------|------|
| BP1 | DispatcherServlet | `doDispatch()` 开头 | 请求入口 |
| BP2 | DispatcherServlet | `getHandler()` | 观察 HandlerMapping 查找 |
| BP3 | DispatcherServlet | `getHandlerAdapter()` | 观察 Adapter 选择 |
| BP4 | RequestMappingHandlerAdapter | `handleInternal()` | 观察参数解析 |
| BP5 | DispatcherServlet | `processDispatchResult()` | 观察结果处理 |

### 📝 操作步骤

1. 发送请求 `GET http://localhost:8080/api/user/1`
2. BP1 命中：观察 `request.getRequestURI()` = `/api/user/1`
3. BP2 命中：
   - 观察 `handlerMappings` 列表（通常有 5-6 个）
   - `RequestMappingHandlerMapping` 匹配成功
   - 返回 `HandlerExecutionChain`，包含 `UserController#getUser` 和拦截器链
4. BP3 命中：`RequestMappingHandlerAdapter` 被选中
5. BP4 命中：
   - 观察参数解析器如何把 `{id}` 从 URL 提取为 `Long id = 1`
   - 反射调用 `getUser(1L)`
6. BP5 命中：
   - `mv` 为 null（`@ResponseBody` 已直接写入 response）
   - 不走视图渲染

## 实验五：观察事务传播行为（REQUIRES_NEW）

### 🎯 目标
验证 REQUIRES_NEW 在外层事务回滚时，内层事务已独立提交。

### 📦 准备代码

```java
@Service
public class OrderService {
    @Autowired
    private LogService logService;
    
    @Transactional
    public void createOrder() {
        // 记录操作日志（独立事务）
        logService.saveLog("创建订单");
        
        // 业务逻辑
        // ...
        throw new RuntimeException("订单创建失败"); // 模拟失败
    }
}

@Service
public class LogService {
    @Transactional(propagation = Propagation.REQUIRES_NEW)
    public void saveLog(String message) {
        // INSERT INTO operation_log ...
        System.out.println("日志已保存: " + message);
    }
}
```

### 🔴 断点位置

| 编号 | 文件 | 方法 | 作用 |
|------|------|------|------|
| BP1 | AbstractPlatformTransactionManager | `getTransaction()` | 观察外层事务创建 |
| BP2 | AbstractPlatformTransactionManager | `handleExistingTransaction()` REQUIRES_NEW 分支 | 观察内层挂起外层 |
| BP3 | AbstractPlatformTransactionManager | `suspend()` | 观察连接挂起 |
| BP4 | AbstractPlatformTransactionManager | `doCommit()` | 观察内层独立提交 |
| BP5 | AbstractPlatformTransactionManager | `processRollback()` | 观察外层回滚 |

### 📝 操作步骤

1. BP1 首次命中：createOrder 的 REQUIRED → 新建事务（连接 A）
2. 进入 saveLog，BP1 再次命中
3. BP2 命中：发现当前有事务 + REQUIRES_NEW
4. BP3 命中：**挂起**连接 A，从 ThreadLocal 移除
5. 新建独立事务（连接 B）
6. saveLog 执行完毕
7. BP4 命中：连接 B **独立提交** ← 日志已持久化！
8. 恢复连接 A
9. createOrder 抛出 RuntimeException
10. BP5 命中：连接 A **回滚** ← 订单数据回滚

### ✅ 预期结果
- `operation_log` 表中 **有** 日志记录（内层已提交）
- 订单表中 **无** 数据（外层已回滚）

## 实验六：观察 Bean 生命周期回调顺序

### 🎯 目标
验证 Bean 生命周期各回调的执行顺序。

### 📦 准备代码

```java
@Component
public class LifecycleBean implements BeanNameAware, BeanFactoryAware,
        InitializingBean, DisposableBean {
    
    public LifecycleBean() {
        System.out.println("1. 构造器");
    }
    
    @Autowired
    public void setDependency(SomeDependency dep) {
        System.out.println("2. 属性注入（@Autowired）");
    }
    
    @Override
    public void setBeanName(String name) {
        System.out.println("3. BeanNameAware.setBeanName()");
    }
    
    @Override
    public void setBeanFactory(BeanFactory factory) {
        System.out.println("4. BeanFactoryAware.setBeanFactory()");
    }
    
    @PostConstruct
    public void postConstruct() {
        System.out.println("5. @PostConstruct");
    }
    
    @Override
    public void afterPropertiesSet() {
        System.out.println("6. InitializingBean.afterPropertiesSet()");
    }
    
    // @Bean(initMethod = "customInit")
    public void customInit() {
        System.out.println("7. 自定义 initMethod");
    }
    
    @PreDestroy
    public void preDestroy() {
        System.out.println("8. @PreDestroy");
    }
    
    @Override
    public void destroy() {
        System.out.println("9. DisposableBean.destroy()");
    }
}
```

### ✅ 预期输出顺序

```
1. 构造器
2. 属性注入（@Autowired）
3. BeanNameAware.setBeanName()
4. BeanFactoryAware.setBeanFactory()
── BeanPostProcessor.postProcessBeforeInitialization ──
5. @PostConstruct
6. InitializingBean.afterPropertiesSet()
7. 自定义 initMethod
── BeanPostProcessor.postProcessAfterInitialization ──
   （AOP 代理在此创建）

── 容器关闭时 ──
8. @PreDestroy
9. DisposableBean.destroy()
10. 自定义 destroyMethod
```
